# You Want More?

A 3D BattleBots intelligence engine built for the **Bright Data × BattleBots** challenge · `#BattleBotsDev`

---

## The one-liner

**A BattleBots fight predictor that shows its work — every probability breaks down into weighted
signals, gets backtested against real fights, and is checked against live web data you can watch
arrive.**

---

## The 30-second pitch

Ask anyone who watches BattleBots who wins Tombstone versus End Game and you get an argument.
Ask the internet and you get a hot take with no numbers behind it.

So we built the opposite of a hot take.

Pick two robots. You watch them fight in 3D — and then you get a number. Not just "Tombstone, 58%",
but *why*: how much of that came from career record, how much from knockout power, how much from the
fact that a horizontal bar eats a lifter for breakfast. Then we show you the receipts. We replayed
the model against every recorded fight in our dataset: it calls 66.7% of them correctly against a
50% coin flip. And when the data itself is in question, we unlock the robot's wiki page live through
Bright Data and diff it against our own numbers, byte count and latency on screen.

It predicts, it explains, it proves it — and when it's a coin flip, it says so.

## The 2-minute version

BattleBots is a sport with real signal in it — career records, knockout rates, and a genuine
rock-paper-scissors layer between weapon classes — and almost nobody has modelled it in the open.
Most "predictors" are either a black box or a vibe. We wanted a third thing: a model simple enough
that you can read the whole formula in one line, and honest enough to publish where it fails.

**What it does.** You pick two robots. A choreographed 3D fight plays out in a WebGL arena — charge,
clash, aftermath, crowned — while the engine produces a win probability, a confidence level, a
projected finish (knockout versus judges' decision), plain-English reasoning, and a Monte Carlo
distribution over 4,000 perturbed trials so you see the *spread*, not one brittle number. From there
you can browse all 42 competitors with procedurally generated 3D models, drill into a per-bot
scouting report generated by running that bot against the entire roster, seed and simulate a
single-elimination bracket as an interactive 3D structure with round-by-round playback, or open the
model's own report card and read the full backtest — including the seasons and the buckets where it
does badly.

**Why the approach is interesting.** Three things are layered so that each one checks the one below
it. The engine is deterministic and inspectable. Bright Data verifies the engine's inputs against
the live web. Two AI layers — a tool-using analyst and a voice commentator — are wired so that they
can only speak numbers the engine or a live fetch actually produced. The AI never gets to be the
source of truth; it gets to be the interface to a source of truth.

**What's genuinely hard about it.** Three things.

First, honest validation. It is trivially easy to backtest a fight predictor and cheat, because
head-to-head record leaks the answer to the fight you're scoring. Our `backtest()` explicitly
disables the head-to-head term for exactly that reason, which costs us accuracy and buys us a number
we can defend.

Second, grounding a language model in numbers. Getting a model to *sound* like a broadcaster is easy.
Getting it to never invent a statistic is not. So the commentator never sees free-form context — it
sees a fact sheet where every entry has an id, a display form and a spoken form, and after generation
we extract every figure from the script, including ones written as words ("seventy-two"), and
reconcile them back against that sheet. Failures get one repair pass; anything still unreconciled is
flagged on screen rather than quietly spoken.

Third, degrading without dying. A live scrape can be slow, a proxy can be blocked, an API key can be
scoped to the wrong model. Every one of those paths has an explicit fallback that reports itself
rather than pretending nothing happened.

## Why it's different

**The model is explainable, not interpretable-in-principle.** There is one formula and it is printed
in the UI:

```
score = 0.45·win_rate + 0.25·ko_rate + 0.30·(0.5 + weapon_edge)
```

Every prediction returns a `contributions` array showing exactly how many points each weighted signal
contributed to each robot. The `/predict` page renders that as a breakdown you can read off. The
analyst is instructed to cite it: not "End Game is better", but "End Game wins on finishing power and
a favourable vertical-versus-horizontal matchup, despite conceding career form".

**It's validated, and the validation is published — failures included.** 66.7% (44 of 66 fights)
against a 50% baseline. Broken out by confidence bucket, by finish method, and by season, with the
complete per-fight sample table on `/model` so you can find every miss yourself. It is above the
coin-flip line in 7 of 8 seasons and clearly below it in one. We show that season.

**The data is verifiable, not asserted.** `/intel` unlocks a robot's live wiki page through Bright
Data and shows the URL, the zone, the byte count, the latency, the timestamp, and whether the response
was live, cached or a fallback — then diffs the parsed fields against our bundled dataset field by
field. Where the wiki and our dataset disagree, the UI says they disagree.

**The AI layers are grounded and audited.** The analyst's tool-call trace is visible in the UI as it
runs: which tool, which arguments, what came back, how many milliseconds. The commentator ships its
fact sheet and its validation report alongside the script. Both are built so that a claim without a
source is structurally impossible to present as verified.

**It admits when it's uncertain — deliberately.** Confidence is derived from the probability margin:
above 20 points is HIGH, above 8 is MEDIUM, below that is LOW. The LOW bucket is where the model is
weakest (58.6%) and we label those matchups as coin flips in the UI, in the analyst's instructions,
and in the commentary voice direction. A predictor that is 67% accurate and tells you which third to
distrust is more useful than one that is 67% accurate and sounds certain about all of it.

## Feature tour (demo order)

**`/` — the arena.** A WebGL hero where scroll position drives the camera through five keyframes,
introducing the three model signals — 0.45 career form, 0.25 finishing power, 0.30 weapon matchup —
one beat at a time. The stat strip is computed, not typed: roster size, match count, seasons,
knockouts, live backtest accuracy.

**`/predict` — the centrepiece.** Pick two bots, hit fight. The 3D scene runs a choreographed bout
(charge, clash, aftermath, crowned) with an impact burst on contact. Alongside it: win probabilities,
confidence, projected finish and knockout likelihood, the weighted signal breakdown, plain-English
reasons, and a Monte Carlo histogram over 4,000 trials — Gaussian noise on the model's own signals,
with the spread widening when the model is less sure. Deterministic PRNG, so the same matchup always
produces the same chart.

**`/roster` — 42 competitors.** Searchable by name, builder and weapon label; filterable by weapon
class. Every robot is drawn from primitives at runtime.

**`/roster/[name]` — the scouting report.** Career stats and leaderboard rank, a signal radar against
the roster baseline, a match-history timeline, and a generated report that runs this bot against all
41 others to surface its best and worst matchups, its strengths, and — stated plainly — its
weaknesses.

**`/leaderboard` — the rankings.** Every column sortable, with search and weapon-class filtering.

**`/tournament` — the bracket.** Seed the top 4, 8 or 16 by win rate — expanded outward the way a real
event does it, so the top two seeds can only meet in the final — then simulate. The bracket renders in
3D with round-by-round playback you can pause and scrub, plus a flat 2D view alongside it.

**`/model` — the report card.** The formula and its weights, headline accuracy against the coin-flip
baseline, calibration by confidence bucket, accuracy split by knockout versus judges' decision,
per-season accuracy against the baseline line, and the complete sample table of every backtested
fight with prediction, actual result and whether we got it right.

**`/intel` — the Bright Data console.** Choose a robot, unlock its wiki page live, and watch the
collection log. You get the parsed payload, the hard provenance panel, and a field-by-field diff
against our bundled dataset. Force a fresh fetch to bypass the cache and prove the number moves.

**`/analyst` — ask it anything.** A streaming, tool-using agent over the engine. Ask "who's overrated
in the horizontal spinner class" and watch it resolve names, call `get_weapon_meta`, call
`predict_matchup`, and answer — with the tool trace rendered live beside the reply and a `Source:`
line naming the tools it used. It can also call Bright Data mid-conversation to pull fresh web data
when you ask for something verified.

### Landing next

Two things are built server-side but not yet exposed as pages, so treat them as in-flight rather than
shipped:

- **`/insights`** — weapon-class meta, biggest historical upsets, and a weapon-versus-weapon advantage
  heatmap. The engine functions (`weaponMeta()`, `upsets()`) and the `/api/weapon-meta` and
  `/api/upsets` endpoints are live and already feed the home page, the model page and the analyst; the
  dedicated page is the remaining piece.
- **`/commentary`** — the AI voice commentator. The full pipeline exists and is callable:
  `/api/commentary/script` builds the grounded fact sheet and the validated six-beat script,
  `/api/commentary/speak` synthesises it with per-beat voice direction, `/api/commentary/transcribe`
  handles voice input. The broadcast-booth UI with synchronised captions and the grounding panel is
  the piece still landing.

## How Bright Data is used

Bright Data's **Web Unlocker** is the collection layer, called through the Bright Data API
(`POST https://api.brightdata.com/request`) with a zone and a target URL, returning raw HTML. It is
used in three distinct places, and it is never a decoration.

**1. Server-side only, credential never exposed.** `BRIGHT_API_KEY` is read exclusively inside
`src/lib/brightdata.ts`, which is imported only by Node route handlers. The browser receives parsed
payloads and provenance — never a token. The API answers HTTP 200 even when the proxy layer rejected
the request, so we read the `x-brd-err-*` headers for the real verdict rather than trusting the status
code.

**2. Real provenance, and a verification diff.** Every unlock returns the URL, the zone name, the
byte count, the round-trip latency in milliseconds, an ISO timestamp, and a status of `live`, `cached`
or `fallback`. Responses are cached for 10 minutes so a demo stays fast and cheap, and the cache is
explicitly labelled as such — plus there's a "force fresh" control that bypasses it. `/intel` then
diffs the parsed page against our bundled dataset field by field (weapon class, weight, builder,
country) and marks each row as agreeing or disagreeing. Disagreements are shown, not smoothed over.

**3. Bright Data as a callable tool for both AI layers.** `scrape_live` is one of the analyst's nine
tools, so the agent can decide mid-conversation to go and check the web, and its instructions require
it to quote the byte count, the latency and the zone as proof the collection was real. Separately, the
voice commentator's fact sheet fires two concurrent unlocks — one per robot — to pull team, builder,
country, season references and the article lede, which the bundled dataset does not contain. Those
facts are tagged `bright_data` in the sheet so the grounding panel can badge them by source.

Parsing is dependency-free: infobox fields, the article lede and season mentions are extracted by our
own parser, with no HTML library in the bundle.

**When Bright Data is unavailable**, nothing breaks. The analyst's tool returns a structured error
telling the model to fall back to the bundled dataset and say so. The commentary fact sheet degrades
to engine-only facts, drops its grounding level to `partial` or `fallback`, and carries a
`degraded_reason` string that the UI can display. A 26-second unlock ceiling means a slow origin can't
hold the broadcast.

## How the AI layers work

### The analyst — a server-side tool-call loop

A streaming agent over `gpt-4o-mini` (overridable via `OPENAI_MODEL`) with nine tools, every one of
them a typed wrapper over the same pure engine functions the pages render, or over the Web Unlocker:

`get_robot`, `predict_matchup`, `get_leaderboard`, `get_weapon_meta`, `get_backtest`, `get_upsets`,
`simulate_tournament`, `scout_robot`, `scrape_live`.

The loop calls the model, streams text deltas straight through, accumulates streaming tool-call
fragments, executes the tools, feeds results back, and repeats — capped at five iterations, with tools
switched off on the final pass so the model has to produce prose instead of looping. Tool telemetry is
emitted twice per call, once on request and once on completion, which is what lets the UI render a
live trace rather than a post-hoc log.

The grounding rule is enforced in three ways at once. The system prompt states that every quantitative
claim must come from a tool result in the conversation and that the dataset is 42 robots and 66
matches, not all of BattleBots history. The tools are the *only* channel through which numbers reach
the model. And every answer ends with a `Source:` line naming the tools used. A tool that throws is
caught and reported back to the model as a structured error, so a failure becomes something the agent
can talk about instead of something that kills the request.

Practical detail that matters more than it sounds: models get robot names slightly wrong constantly
("witch doctor", "Tombstone Bot", "Minotaurus"). Name resolution goes exact → case-insensitive →
substring → Levenshtein distance with a one-typo-per-four-characters tolerance, and an unresolvable
name returns `did_you_mean` candidates with an instruction to retry. A near miss is recoverable rather
than fatal.

### The commentator — fact sheet, then script, then speech

**Stage 1: the fact sheet.** Built server-side from the prediction engine (records, rates, weapon
edge, probabilities, weighted contributions, the dominant signal behind the call, the Monte Carlo 90%
spread) plus two concurrent Bright Data unlocks. Every entry carries an id, a label, a display form,
a spoken form, a numeric value where one exists, and a source tag (`roster`, `engine`, `simulation`,
`bright_data`). This sheet is the only thing the model is allowed to draw numbers from.

**Stage 2: the script.** The model returns six beats — intro, tale of the tape, prediction, clash,
finish, verdict — under a strict JSON schema, so there is no prose to parse. Beats are normalised into
fixed order, run through deterministic speech cleanup (markdown stripped, emoji stripped,
`snake_case` unwrapped, bare numerals and records converted to spoken words), and durations are
clamped against word count at broadcast pace.

**Stage 3: numeric validation.** Every figure in every beat is extracted — digits and number-words
alike — and reconciled against the fact sheet within half a percentage point of rounding slack. Small
integers (0–3) are allowed through as natural counting words; that hole is deliberate and documented.
Beats that fail get one repair pass, and the rewrite is only accepted if it is genuinely cleaner.
Anything still unreconciled sets a `flagged` bit with a reason, so the UI can warn the audience
instead of quietly lying to them. Fact ids the model cites that don't exist on the sheet are stripped
and reported, because a dangling citation is a false claim of proof.

**Stage 4: speech.** Text-to-speech via `gpt-4o-mini-tts` with per-beat delivery instructions — the
tale-of-the-tape beat is directed to slow down and let each figure land; the clash beat is directed to
be explosive; the verdict beat is directed to deliver admitted uncertainty with genuine candour rather
than glossing over it. Six curated voices. Voice input for driving the booth prefers the browser's own
`SpeechRecognition` and falls back to a server transcription route for Firefox and Safari.

Every stage has a floor under it. No API key, an unreachable model, or a key scoped to the wrong model
family all land on a deterministic template script built from the same fact sheet — fact-checked by
construction, and labelled `synthetic: true` so the UI can be honest about it.

| Layer | Tech |
|---|---|
| Framework | Next.js 16 (App Router), React 19, TypeScript strict |

The prediction engine has no I/O and no dependencies. Everything the UI shows — pages, API routes,
analyst tools, commentary fact sheet — is derived from the same pure functions, which is why the
analyst cannot disagree with the page.

## The model, honestly

**The formula.**

```
score = 0.45·win_rate + 0.25·ko_rate + 0.30·(0.5 + weapon_edge)
```

Head-to-head history then applies a symmetric nudge of ±0.05 per prior win. Scores are normalised
across the two robots into probabilities. Confidence comes from the margin: HIGH above 20 points,
MEDIUM above 8, LOW below that. Projected finish comes from a knockout-likelihood term driven by both
bots' knockout rates and how lopsided the weapon matchup is.

`weapon_edge` is a hand-built 8×8 class-versus-class table in the range -1 to +1 — a horizontal
spinner is +0.35 against a lifter, a lifter is -0.35 against a horizontal spinner. It is antisymmetric
by construction.

**The backtest.** Replay the model over every recorded fight where both robots are in the roster.
Head-to-head is disabled during backtesting, so the model cannot peek at the result of the fight it
is being asked to predict.

| | Accuracy | Sample |
|---|---|---|
| Overall | **66.7%** | 44 / 66 |
| Coin-flip baseline | 50.0% | — |
| HIGH confidence | 80.0% | 4 / 5 |
| MEDIUM confidence | 71.9% | 23 / 32 |
| LOW confidence | 58.6% | 17 / 29 |
| Fights that ended by KO | 84.6% | 22 / 26 |
| Fights that went to the judges | 55.0% | 22 / 40 |

Above the baseline in 7 of 8 seasons. The exception is 2019, at 42.9% on 7 fights.

**Where it's weak — stated plainly.**

- **The sample is small.** 66 fights across 42 robots. That is enough to beat a coin flip
  convincingly and not enough to claim precision. The HIGH-confidence bucket in particular holds only
  five fights, so treat its 80% as directional, not as a measured rate.
- **The dataset is curated, not exhaustive.** It is a hand-assembled slice of notable BattleBots
  results from 2016 to 2024 (2017 is absent), not the whole history of the sport. Every AI layer is
  instructed to say so rather than imply otherwise.
- **Judges' decisions are the model's blind spot.** 84.6% on knockouts versus 55.0% on decisions. That
  gap is the honest story of this model: it reads damage well and it reads control, aggression and
  judging panels poorly. Fixing that needs per-fight control and damage data we don't have.
- **The weights are hand-set, not fitted.** 0.45 / 0.25 / 0.30 are reasoned, not learned. Fitting them
  on 66 fights would overfit; we chose to keep them interpretable and disclose that choice.
- **`weapon_edge` is expert judgement.** It encodes how the sport actually plays out, but it is a
  hand-built matrix, not a measurement.
- **The model is stateless in time.** Career win rate is a lifetime aggregate, so it doesn't know that
  a bot was rebuilt between seasons or arrived at an event with a new weapon.
- **Monte Carlo widens the picture; it does not add information.** It perturbs the same three signals.
  It is an honest uncertainty range around the model's own view, not an independent estimate.

## Try it

```bash
cd app
npm install
npm run dev
```

Open http://localhost:3000. It runs fully offline against the bundled dataset — predictions, the
backtest, the roster, brackets and all 3D views work with no credentials at all.

To enable live collection and the AI layers, copy `.env.example` to `.env` in the repo root (or to
`app/.env.local`) and set:

| Variable | Enables |
|---|---|
| `BRIGHT_API_KEY` | Bright Data Web Unlocker — `/intel`, the analyst's `scrape_live` tool, live commentary facts |
| `BRIGHTDATA_ZONE` | Your Web Unlocker zone name |
| `OPENAI_API_KEY` | The `/analyst` agent and the commentary script, voice and transcription routes |

Optional overrides: `OPENAI_MODEL` for the analyst, `OPENAI_COMMENTARY_MODEL` for script generation,
`OPENAI_TTS_MODEL` for voice. Free Bright Data hackathon credits: https://brdta.com/battlebotsdev

Both `.env` files are gitignored. No credential is ever read outside a server route handler.

```bash
npm run typecheck   # strict TypeScript, no emit
npm run build       # production build
```
